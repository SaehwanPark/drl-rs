## Executive assessment

**Disposition: `fix`. Major steering correction is necessary; an architecture
restart is not.**

The deterministic core, explicit RNG, replay metadata, stable content IDs,
fair observation boundary, browser/MCP projections, and repository checks are
good foundations. They should be preserved. The problem is the recent unit of
progress: development is repeatedly closing individual counter values and
boundary projections while larger semantic rules and compatibility boundaries
remain unresolved.

The immediate risk is not that the rewrite is infeasible. It is that a long
sequence of locally correct micro-slices can create substantial code and
verification fan-out without materially reducing the remaining canonical
behavior gap. The next work therefore needs to close whole semantic branches,
bind persistent histories to their interpreter identity, and put exit criteria
on expensive safety backstops.

## Findings

### 1. Chainfire slices are enumerating a rule instead of implementing it

The pinned legacy firing path classifies chainfire by state:

- level `0`: reduce the base volley by `base_shots div 3`;
- level `1`: use the base volley;
- levels `2..255`: add `base_shots div 2`;
- increment the chain state until it saturates at `255`.

It also reduces an under-supplied volley to the ammunition that can actually
be fired and accepts the action when at least one projectile remains. At the
checkpoint, Rust uses weapon-specific, level-enumerated profiles, rejects the
next unlisted level, and rejects a clip below the aggregate full-volley cost.
The source facts are visible in the pinned Pascal `src/dfbeing.pas:1484-1517`;
the Rust branch is concentrated around
`crates/drl-core/src/behavior.rs:960-1155` and
`crates/drl-core/src/game.rs:1767-1898`.

The Rust policy may intentionally differ from legacy, but atomic rejection does
not require that difference. An accepted partial volley can be planned and
committed atomically. The current documentation instead treats full-volley
under-supply rejection as if it followed from the transaction invariant.

**Required steering:** no further PR whose primary outcome is “add the next
chainfire level.” The next M9 chainfire work must define one typed transition
model for the complete evidenced state classes, saturation, ammunition policy,
target continuation/routing, reset behavior, and weapon traits. Canonical
differences must be named as DRL-Rust decisions, not justified indirectly by
atomicity. Table/property tests should cover equivalence classes and boundaries
rather than copying every plateau through every boundary.

### 2. Browser saves version syntax but not gameplay interpretation

Replay V2 records gameplay, RNG-sampling, generator, and ruleset identities and
rejects incompatible histories. Browser snapshots do not. The shipped V2 token
contains only the snapshot version, fixed-content label, command count, and
commands (`crates/drl-web/src/persistence.rs:188-274`). Restore constructs the
current fixed session and resubmits the old commands under current rules
(`crates/drl-web/src/lib.rs:525-539`).

Consequently, a syntactically valid localStorage token can be silently
reinterpreted after a gameplay-semantics change. Successful replay of its
commands only proves that the current engine accepts them; it does not prove
that the saved session means what it meant when written.

**Required steering:** M10 snapshot V3 is the active implementation slice.
It must bind the token to the same semantic identities that interpret the
history, reject unsupported identities before command execution, restore in
temporary state, and commit only after complete success. Because V1/V2 tokens
do not reveal which gameplay semantics wrote them, they must not be assigned a
semantics identity by guesswork. They require explicit fail-closed handling or
a separately evidenced migration policy.

### 3. The atomicity backstop has no measured exit path

`Game::step` clones the complete state before every command and restores it on
error (`crates/drl-core/src/game.rs:217-232`). `BrowserSession::submit` then
clones the game again around that already-transactional boundary
(`crates/drl-web/src/lib.rs:482-505`). The accepted steering decision calls the
core clone an interim backstop and discourages unconditional full-state cloning
for cohort workloads, but no throughput or allocation budget was found.

This is correct as a safety net and should not be removed without equivalent
evidence. It is not yet a finished transaction architecture.

**Required steering:** before materially expanding M11 cohort scale or adding
another wrapper rollback, establish a representative command-throughput and
allocation baseline, identify the owner of transactionality at each boundary,
remove redundant outer snapshots where the core contract suffices, and migrate
the hottest accepted paths toward validate/prepare/commit. Exact pre/post
equality tests remain mandatory throughout.

### 4. Canonical documents became an append-only delivery ledger

`SPEC.md` says it expands exactly one active implementation slice, yet most of
its 5,476 lines record historical slices and multiple headings still say
`Current`. The roadmap's first “Latest Delivered” item also points to older
M5/M6/M13 work rather than the audited M9 checkpoint. This makes current scope
harder to distinguish from delivered evidence and weakens review.

**Required steering:** keep `SPEC.md` bounded to one active slice. Delivered
history belongs in the roadmap, changelog, audit/evidence notes, and Git. Do not
append the next delivered slice below the old one. Replace the active contract
when scope changes and add automated structural checks if drift recurs.

### 5. The process requires independent review, but the latest PR has no
observable review record

The team specification requires a determinism review before final acceptance.
PR #426 reports no GitHub reviews, no review decision, and the `main` branch is
not protected. The hosted checks are strong and passed, but they do not replace
an independent comparison of legacy evidence, semantics, transactionality, and
claims.

This audit cannot prove that no off-platform review happened; it can only state
that no attributable review was observable in the PR or checked repository
history at the checkpoint.

**Required steering:** every replay-visible or legacy-fidelity slice must carry
an attributable `pass`/`fix`/`blocked` determinism-review result linked in its
handoff or PR. Before 1.0, record and enforce the repository's decision on
required reviews and branch protection rather than relying on convention.

### 6. Module concentration is now a change-amplification warning

The largest browser, MCP, scenario, and special-item modules contain multiple
reasons to change. Line count alone is not a refactoring mandate. Repeated
cross-boundary edits for one mechanic, however, show that policy, projection,
fixtures, and compatibility checks are expensive to review as one unit.

**Required steering:** split a large module only when the active slice exposes
a stable responsibility boundary. Prefer focused modules and shared pure
contracts over new crates or a general callback/plugin framework. Do not begin
an unrelated “big modularization” project.

## Steering sequence

The following order applies until the post-audit gates close:

1. **M10 — Semantics-bound browser snapshot V3** (active in `SPEC.md`).
2. **M9 — Chainfire semantic consolidation** as one evidenced state-machine
   slice; no additional counter-level PRs.
3. **M1/M11 — Transaction cost baseline and rollback ownership**, followed by
   bounded prepare/commit work where measurement justifies it.
4. **M0 — Enforce bounded canonical documents and attributable independent
   review** for semantics-bearing slices.
5. Resume vertical canonical-fidelity slices that close complete behavior
   branches.
6. Resume broad scalar content, unrelated platform/tooling expansion, and
   larger cohort workloads only after their relevant gates close.

Controlled reference capture remains valuable whenever the required Linux
x86-64 environment becomes available, but unavailable capture work remains
`NOT_RUN` rather than blocking source-grounded corrective work.
