# DRL-Rust Architecture and Development Audit — 2026-08-23

Baseline: `SaehwanPark/drl-rust` at
`6783f87439ee2708c7d46e2d15d899e7f4b8d9f8`, project version `0.2.88`.

## Executive assessment

The rewrite is feasible and the major architectural direction is strong. The
functional-core/imperative-shell split, semantic command/event/observation
interfaces, explicit RNG, replay/scenario tooling, fair observation boundary,
build-time legacy-content extraction, and repository validation harness are all
sound foundations.

The main risk has shifted from feasibility to development trajectory. Tooling,
release infrastructure, browser support, and scalar content breadth are now
advancing faster than canonical gameplay behavior. Before broad content
migration continues, the project should close several correctness and
scalability gaps that would otherwise become increasingly expensive.

## High-priority findings

### 1. Rejected-command atomicity is documented but not universally enforced

The architecture states that rejected commands do not modify simulation state,
but current command implementations can mutate before all expected validation
has completed. Confirmed examples from the reviewed baseline include:

- ranged attack ammunition can be decremented before an out-of-range target is
  rejected;
- equipping an item can remove it from inventory before discovering that the
  item has no equipment slot.

This should become an executable invariant: when `Game::step(command)` returns
`Err`, the complete post-state, including RNG state, must equal the pre-state.
The preferred implementation shape is immutable validation/preparation followed
by a commit phase.

### 2. RNG bounded sampling should be corrected before replay semantics harden

The current bounded integer sampler uses modulo reduction. That is biased unless
the requested span divides the generator domain evenly. The project should move
to an unbiased bounded sampler and pin raw and derived RNG golden vectors before
replay streams become long-lived compatibility artifacts.

### 3. Current replay verification is local determinism, not cross-version compatibility

Running the same replay twice on the current implementation is valuable, but it
only proves repeatability under the current semantics. Old replay item spawns
and other rules can be reconstructed through current definitions, so unchanged
wire schema does not guarantee unchanged historical interpretation.

Replay metadata should distinguish wire/schema version, gameplay semantics
version, and content/ruleset semantics. Procedural generation should be included
in that compatibility contract or receive its own semantics version.

### 4. Content registration has growing change amplification

Recent content additions require synchronized edits across several enums,
definition tables, validation lists, replay codecs, display mappings, assets,
and documentation. Compiler exhaustiveness is useful; manual duplication is
not. Ordinary content identity should have one authoritative compile-time
catalog from which routine projections are generated or derived.

### 5. The difficult migration problem is behavior, not scalar data

The legacy Lua ecosystem exposes many hooks and callback-heavy items. Static
fields can be converted mechanically, but doing so does not solve alternate
fire/reload behavior, equip effects, set bonuses, recharge, periodic healing,
on-hit/on-kill effects, costs, or special-level state machines.

The rewrite should define a bounded typed Rust behavior vocabulary and
stress-test it against deliberately difficult legacy examples before resuming
mass scalar-only migration. A generic string-keyed event bus or recreated Lua
callback system would reproduce the wrong kind of flexibility.

### 6. `drl-protocol` currently mixes stable contracts with gameplay policy

Stable IDs, commands, observations, events, and replay wire types fit naturally
in `drl-protocol`. Balance values and behavior definitions do not belong there
merely because a semantic identity crosses a boundary. Move gameplay policy
into `drl-core` or an explicit domain/content boundary while keeping protocol
IDs stable.

### 7. Large modules are becoming new concentration points

`drl-web`, `drl-render`, and portions of `drl-core` have grown large enough that
multiple independent reasons to change share one module. Prefer module-level
separation by responsibility before adding new crates. Crates should enforce a
meaningful dependency boundary, not function as a line-count remedy.

### 8. `drl-script` naming no longer matches accepted runtime architecture

Runtime Lua is prohibited by the accepted build-time migration direction.
`drl-script` currently functions as a placeholder/content-conversion boundary.
If that remains its purpose, remove it until needed or rename it to a name such
as `drl-content-import` so the crate name does not imply a runtime scripting
capability.

### 9. Rights inventory should separately track legacy creative text

The current release-rights boundary clearly distinguishes project-authored code,
legacy graphics, excluded legacy code, and unresolved media. Rust definitions
also contain legacy-derived descriptive text. Creative text should receive an
explicit provenance/redistribution status rather than silently inheriting the
project-code license. This is a clearance question, not a legal conclusion.

## Development steering implication

The next development center of gravity should be:

1. command atomicity and generic rejection invariants;
2. unbiased RNG plus explicit replay semantics;
3. single-source content registration;
4. typed legacy behavior model proven on difficult examples;
5. protocol/domain ownership cleanup;
6. vertical canonical-fidelity slices;
7. only then renewed broad content migration and unrelated infrastructure
   expansion.
