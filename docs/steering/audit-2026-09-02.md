## Status

**Recommendation:** APPROVE WITH BOUNDED IMPLEMENTATION

The current `drl-rs` architecture is suitable for native Fedora support without changing the deterministic gameplay model or browser-first 1.0 product direction.

The recommended strategy is to:

* establish Fedora as a first-class development environment now;
* incubate a native desktop frontend using `winit + wgpu`;
* initially target Fedora 43 + GNOME/Mutter Wayland + Mesa/RADV Vulkan;
* validate the same native frontend on macOS/Metal;
* defer Fedora browser/WebGPU support until the existing browser product is substantially more mature.

Native Fedora support should be treated as a **new platform shell**, not as a port or fork of the game engine.

---

# 1. Architectural Finding

The existing architecture already provides the required portability boundary.

Relevant responsibilities are separated approximately as:

```text
drl-core
  deterministic simulation

drl-protocol
  commands, observations, events, replay contracts

drl-render
  platform-neutral presentation and RenderScene construction

drl-app
  native headless CLI/tooling

drl-mcp
  native MCP integration

drl-web
  browser/WASM/WebGPU/DOM shell

drl-audio
  semantic audio cues + current Web Audio implementation
```

The deterministic core does not depend on macOS, browser APIs, graphics APIs, filesystem behavior, or native windowing.

This architecture MUST be preserved.

---

# 2. Scope Decision

## MUST

The current **browser-first 1.0 product direction MUST remain unchanged** unless separately reconsidered.

The native desktop work MUST be treated as pre-1.0 platform incubation rather than an additional 1.0 release requirement.

Initial Linux support MUST target a concrete environment:

```text
Fedora 43
GNOME / Mutter
Wayland
Mesa / RADV
Vulkan
```

The project MUST NOT initially claim generic Linux desktop support.

## SHOULD

The same native frontend SHOULD also be exercised on macOS through `wgpu`'s Metal backend.

This provides an important portability check:

```text
                  drl-desktop
                       |
                    wgpu
                  /      \
             Vulkan      Metal
             Fedora      macOS
```

## MAY

Broader Linux distributions, X11, NVIDIA-specific validation, Flatpak, RPM packaging, and other desktop environments MAY be added later.

---

# 3. Immediate Maintainability Finding

`crates/drl-web/src/lib.rs` has accumulated too many responsibilities and has become a very large frontend module.

It currently contains or coordinates concerns including:

* browser session orchestration;
* DOM behavior;
* input handling;
* accessibility projections;
* animation timing;
* WebGPU lifecycle;
* shader/rendering integration;
* browser-specific state;
* substantial test coverage.

## MUST

The project MUST NOT create `drl-desktop` by copying large portions of `drl-web`.

Browser-specific responsibilities MUST remain browser-specific.

Gameplay and presentation policy MUST NOT migrate into platform shells to facilitate reuse.

## SHOULD

Before or alongside native frontend work, `drl-web` SHOULD be decomposed into focused modules.

Candidate boundaries include:

```text
drl-web/
  session
  input
  dom
  accessibility
  persistence
  animation
  gpu
  texture
  wasm
```

Exact module names are not prescribed.

The objective is separation of responsibilities, not decomposition for its own sake.

---

# 4. Shared Frontend Boundary

The preferred dependency direction is:

```text
                 drl-core
                    |
              drl-protocol
                    |
                drl-render
                    |
          platform-independent scene
                    |
        +-----------+-----------+
        |                       |
     drl-web               drl-desktop
 browser shell             native shell
```

## MUST

Both browser and native frontends MUST consume the same authoritative:

* `Command`;
* observations;
* game events;
* `PresentationStep`;
* `RenderScene`;
* stable asset identities;
* semantic audio cues where applicable.

`drl-desktop` MUST NOT implement alternative gameplay rules.

`drl-desktop` MUST NOT read hidden core state when an existing fair observation or presentation projection exists.

Presentation timing MUST NOT affect deterministic simulation state.

## SHOULD

Shared GPU implementation MAY be extracted only where actual backend-independent reuse exists.

A possible future structure is:

```text
drl-render
    |
    v
drl-gpu
    |
    +--> drl-web
    |
    +--> drl-desktop
```

However, `drl-gpu` SHOULD NOT be created merely to satisfy architectural symmetry.

Reuse SHOULD be demonstrated before introducing the additional crate.

## MUST NOT

`wgpu`, native windowing, browser APIs, filesystem APIs, or audio device APIs MUST NOT be introduced into `drl-core`.

`drl-render` MUST remain a platform-neutral presentation layer rather than becoming a windowing or OS integration crate.

---

# 5. Fedora Development Support

Fedora SHOULD become a supported development host before native desktop productization proceeds far.

Current repository tooling is already largely compatible with POSIX/Linux environments.

## MUST

CI MUST gain a complete Linux repository verification path.

The Linux job MUST exercise the same relevant repository-wide contracts as macOS, including:

* formatting;
* Clippy;
* workspace tests;
* deterministic/replay tests;
* repository shell checks;
* MCP integration checks;
* content and structural validation.

## SHOULD

A Fedora 43 container or equivalent Fedora CI environment SHOULD additionally be used where practical.

Recommended conceptual matrix:

```text
Repository verification

macOS
  └── full repository checks

Linux
  └── full repository checks

Fedora 43
  └── targeted development-environment checks
```

The Fedora-specific job does not need to duplicate every generic Linux test if doing so provides no additional evidence.

---

# 6. New Native Desktop Crate

Create a native frontend provisionally named:

```text
crates/drl-desktop
```

## MUST

The first implementation MUST remain thin.

Expected initial responsibilities:

* `winit` application/event loop;
* native window creation;
* `wgpu` surface/device initialization;
* keyboard input translation;
* framebuffer resize handling;
* scale-factor handling;
* rendering of existing `RenderScene` values;
* presentation of the existing playable loop.

Recommended stack:

```text
window/input: winit
rendering:    wgpu
Fedora GPU:   Vulkan
macOS GPU:    Metal
```

## MUST NOT

The first milestone MUST NOT include unrelated platform productization work such as:

* full save system;
* native audio;
* launcher;
* configuration GUI;
* menus;
* installer;
* RPM;
* Flatpak;
* gamepad support;
* X11 compatibility;
* generic Linux compatibility;
* desktop accessibility implementation.

These concerns MUST remain separate follow-up slices.

---

# 7. First Native Acceptance Milestone

The initial native milestone SHOULD answer one question:

> Can the existing deterministic game and presentation contracts drive a native `winit + wgpu` frontend without duplicated gameplay or presentation policy?

Acceptance SHOULD require:

1. A native window launches successfully.
2. An existing deterministic game/session can be created.
3. An existing `RenderScene` is rendered through `wgpu`.
4. Keyboard input is converted into existing semantic `Command` values.
5. A basic playable loop works.
6. Window resizing works.
7. Wayland scale-factor changes do not corrupt rendering.
8. Pixel-art sampling remains nearest-neighbor.
9. The implementation runs on Fedora 43 / Wayland / Vulkan.
10. The same desktop frontend is verified on macOS / Metal.
11. No native-specific gameplay branch is introduced.
12. Existing replay/determinism behavior remains unchanged.

This milestone SHOULD be considered an architectural proof rather than a desktop release.

---

# 8. Wayland and Pixel Scaling

GNOME/Wayland fractional scaling requires explicit handling for pixel-art rendering.

## MUST

Rendering MUST use the physical framebuffer size supplied through the window/surface abstraction.

The game SHOULD select the largest integer render scale that fits the available framebuffer.

Unused space SHOULD be letterboxed rather than stretching game pixels fractionally.

Textures MUST use nearest-neighbor sampling for pixel-art output unless a specific asset requires otherwise.

Conceptually:

```text
Wayland logical window
        |
        v
window scale factor
        |
        v
physical framebuffer
        |
        v
largest fitting integer game scale
        |
        v
nearest-neighbor scene
```

## MUST NOT

Simulation dimensions or gameplay state MUST NOT depend on compositor scale factors.

---

# 9. Native Assets and Persistence

The browser frontend currently naturally relies on browser-oriented loading and persistence mechanisms.

Native equivalents MUST remain platform-shell concerns.

## SHOULD

Native asset loading SHOULD consume the same stable asset identities and metadata already used by presentation code.

The desktop shell MAY initially use development filesystem paths or embedded resources.

A generalized asset-provider abstraction SHOULD be introduced only if the browser and native implementations demonstrably benefit from it.

## MAY

Native persistence can later use an OS-appropriate application data directory.

Save compatibility MUST remain governed by existing semantic/replay compatibility contracts rather than by frontend-specific assumptions.

---

# 10. Native Audio

Current playback is Web Audio-specific.

The semantic cue layer should remain shared.

Preferred long-term shape:

```text
GameEvent
   |
   v
AudioCue
   |
   +--> WebAudio backend
   |
   +--> Native audio backend
```

## MUST

Native audio MUST NOT alter gameplay semantics or event ordering.

Audio failure MUST NOT become gameplay failure.

## SHOULD

A native implementation SHOULD be introduced only after the initial rendering/input milestone succeeds.

Potential Rust backends MAY include lightweight `cpal`-, Kira-, or rodio-based implementations after evaluating project needs.

No specific library is mandated by this audit.

---

# 11. Fedora Browser Support

Fedora browser/WebGPU support is explicitly deferred.

## MUST

Fedora browser compatibility MUST NOT become a requirement for the native Fedora development effort.

Linux browser-specific GPU/Chromium issues MUST NOT block native desktop progress.

## SHOULD

Browser development SHOULD continue against the current primary environment until the browser edition becomes substantially more mature.

Fedora browser support SHOULD be reconsidered later as a separate compatibility effort.

This avoids conflating:

* DRL browser frontend defects;
* Chromium Linux WebGPU behavior;
* AMD/Mesa browser-driver behavior;
* Linux browser packaging/environment issues;
* native Fedora support.

---

# 12. Process Guidance

The repository's determinism, evidence, and review discipline remains valuable.

However, native frontend work SHOULD avoid excessive semantic micro-slicing where no gameplay semantics are changing.

## MUST

Changes affecting deterministic gameplay or replay interpretation MUST continue to follow existing determinism/review requirements.

## SHOULD

Pure frontend/platform work SHOULD use evidence proportional to its actual risk.

For example:

* a Wayland resize fix should demonstrate rendering/resize behavior;
* it SHOULD NOT require invented gameplay-semantic evidence when gameplay is unaffected.

The control plane SHOULD help review implementation rather than become the implementation objective.

---

# 13. Recommended Implementation Order

Developers SHOULD proceed approximately as follows:

1. **Refactor `drl-web`**

   * separate browser-specific responsibilities;
   * identify genuinely reusable frontend logic.

2. **Establish Linux CI**

   * run full repository verification on Linux;
   * add Fedora-specific checks where they provide additional evidence.

3. **Define the native frontend boundary**

   * preserve `drl-core`, `drl-protocol`, and `drl-render` ownership.

4. **Create `drl-desktop`**

   * minimal `winit + wgpu` application shell.

5. **Deliver Fedora Wayland/Vulkan proof**

   * rendering;
   * input;
   * resizing;
   * integer pixel scaling.

6. **Verify macOS/Metal**

   * same crate;
   * same presentation/game contracts.

7. **Extract shared GPU infrastructure only if justified**

   * avoid premature abstraction.

8. **Add native persistence**

   * separate bounded slice.

9. **Add native audio**

   * separate bounded slice.

10. **Productize later**

    * packaging;
    * broader Linux support;
    * accessibility;
    * gamepad;
    * distribution.

---

# 14. Roadmap Language

Recommended roadmap distinction:

## Browser-first 1.0 product scope

* desktop Chromium browser;
* deterministic headless CLI;
* MCP and automation/tooling support.

## Pre-1.0 native desktop incubation

* Fedora 43 development support;
* `drl-desktop`;
* Wayland/Vulkan rendering;
* macOS/Metal verification;
* architecture validation.

## Post-1.0 native productization

* native audio;
* native persistence polish;
* accessibility;
* packaging;
* broader Linux compatibility;
* distribution and release support.

Native incubation MUST NOT implicitly expand the 1.0 release gate.

---

# 15. Final Audit Decision

**Proceed.**

Fedora-native Wayland/Vulkan support is compatible with the current architecture and does not require redesigning the deterministic game engine.

The primary implementation risks are frontend organization and platform I/O, not gameplay portability.

Developers MUST preserve the following invariants:

1. `drl-core` remains platform-independent and deterministic.
2. `drl-render` remains platform-neutral.
3. Native and browser clients consume shared semantic/presentation contracts.
4. No gameplay or presentation-policy fork is introduced for Fedora.
5. `drl-web` is refactored rather than copied.
6. Linux CI is established early.
7. The first native milestone stays deliberately small.
8. Fedora browser support remains deferred.
9. Native incubation does not enlarge the browser-first 1.0 commitment.
10. Cross-platform desktop support is demonstrated through one `drl-desktop` implementation running on Fedora/Vulkan and macOS/Metal.

Overall architectural risk: **LOW**

Expected implementation effort: **MODERATE**

Recommended priority: **APPROVED after/alongside frontend modularization and Linux CI**
